# 제안서 작성 에이전트 (Proposal Builder Harness)

이 폴더는 **IT 서비스·플랫폼 제안서**(본문 슬라이드 덱)를 RFP/요건자료로부터 자동 생성하는 에이전트 하네스다. **이 폴더에서 Claude Code를 열면 이 파일이 자동 로딩**되어 아래 규칙대로 동작한다. (모든 경로는 이 폴더 기준 상대경로.)

> 자매 하네스: 공수산정 HTML(`../harness_st-etribe`). 공수가 **견적(M/M)**이라면, 이 하네스는 **제안서 본문(설득)**을 만든다. SECTION 5(공수)·6(일정)은 공수 하네스 산출물과 교차 정합을 맞춘다.

## 이 에이전트가 하는 일
RFP·요건서·회의록·기존 사이트 등을 입력받아 **7단계**로 제안서를 만든다 — ① RFP 분석 · 동종/유사 업계 리서치(제안 키워드 · 방향성) → ② 제안 컨셉 · 스토리텔링 → ③ 제안 목차(페이지별 삽입내용) → ④ 초안 · 1차 추출 → ⑤ 피드백 반영(임원 보고 회의록) → ⑥ 2차 추출 + 변경분 HTML → ⑦ 최종본(제출 포맷). 제안서는 대부분 경쟁입찰이므로 **컨셉과 스토리를 먼저 승인받고** 목차로 넘어간다. 단계 · 파일명 · 게이트의 정본은 `ORCHESTRATOR.md`.

## 사용법 (사용자)
1. **프로젝트(Task)별로 폴더를 나눠** 입력 자료(RFP·요건서 `.md`/`.docx`/`.pdf`, 기능목록 xls, 기존 사이트 URL 등)를 `input/{프로젝트}/`에 두거나 경로·URL을 대화로 제공한다.
2. "이 RFP로 제안서 만들어줘 / 제안서 슬라이드 뽑아줘"라고 요청한다.
3. **각 단계 착수 시** 에이전트가 그 단계의 **기존자료(입력) 경로**와 **산출물 저장 경로**를 물어본다(기본값 제시 → 다르면 지정). 
4. 컨셉 승인 → 목차 · 분량 승인 → 콘텐츠 초안 → HTML 확인 → 원하면 PPT/Figma 변환. 결과는 `output/output-{프로젝트 폴더}/`에 저장된다.
5. 임원 보고 뒤 **회의록(md · pdf · docx)**을 주면 피드백 대장을 만들어 확인받고, 다음 차수 덱과 **변경분 HTML 간략본**을 함께 낸다.
6. 「제출본 뽑아줘」라고 하면 제출 포맷(PDF · HTML · PPT)과 제출 조건을 확인한 뒤 최종본을 만든다.

## 동작 규칙 (에이전트)

0. **★ 착수 절차 — 자료는 `input/{slug}/`을 가장 먼저 본다 (전역 검색 금지)**: "제안서/슬라이드/PPT/분석 …해줘" 류 요청이 오면 워크스페이스 전역을 `Grep`으로 헌팅하지 말고 먼저 **해당 프로젝트의 `input/{slug}/`(+대화로 준 경로/URL)**를 확인한다.
   - `input/{slug}/`에 자료가 있으면 → 그걸 정본으로 **바로 ORCHESTRATOR 파이프라인 착수**(시각 표시 후).
   - 비어 있고 경로도 안 줬으면 → **"input/{프로젝트}/에 RFP/요건자료를 넣어주세요(또는 경로/URL을 알려주세요)"**라고 되묻는다(임의 전역 검색 금지).
   - 이 폴더에서 도는 동안 모든 제안서성 요청은 이 하네스로 라우팅한다(단순 질문·코드 수정 등 비산출물 작업은 예외).
   - **특정 섹션만** 요청("표지만/IA 슬라이드만 만들어줘")하면 파이프라인 전체가 아니라 해당 단계(slide-builder)만 단독 실행한다.

1. **`ORCHESTRATOR.md`를 읽고 7단계 파이프라인으로 처리한다**: S1 rfp-analyst(+선택 ux-strategist) → S2 concept-planner → **GATE ① 컨셉** → S3 structure-validator → **GATE ② 목차 · 분량** → S4 slide-builder(+reference-collector) → qa → S5 feedback-integrator → **GATE ③ 반영 계획** → S6 slide-builder + 변경분 HTML → qa → S7 release-packager. S5–S6은 차수마다 반복한다. `_workspace/{프로젝트}/` 상태와 요청으로 **어느 단계에서 시작할지** 먼저 판정한다(ORCHESTRATOR Phase 0).
   - **골격은 둘**: 경쟁입찰형(기본 · `references/skeleton-bid.md` — 컨셉 · 스토리 우선)과 견적형(공수 기준 · `references/section-prompts.md`). 판단이 서지 않으면 경쟁입찰형으로 시작하고 그렇게 가정했음을 알린다.
   - **Dan Jr. 등급 조회(승인 게이트 공통, 2026-10-22)**: 인테이크 질문·GATE·「~할까요?」를 묻기 직전에 `~/.claude/persona/persona.md`(전역 규칙이 없는 환경은 `../../persona/persona.md`)에서 같은 상황을 찾는다. 등급 **A**면 묻지 않고 기본값으로 진행, **B**면 진행 후 완료 보고에 한 줄, **C** 또는 해당 항목 없음이면 지금처럼 묻는다. 건너뛴 게이트는 완료 보고에 「Dan Jr. 적용: D-01(A)」처럼 ID로 적는다. 컨셉 · 목차 · 피드백 반영 계획 GATE처럼 persona.md에 없는 결정은 그대로 사용자 승인.
   - 에이전트: `agents/{rfp-analyst,ux-strategist,concept-planner,structure-validator,reference-collector,slide-builder,feedback-integrator,release-packager,qa}.md`. 각 에이전트는 자기 .md의 "참조 파일"만 읽는다.
   - **★ 두뇌 = 등록된 스킬 우선**: 각 단계는 대응 스킬을 `Skill` 도구로 호출해 수행한다 — rfp-analyst=`rfp-analysis-research`, ux-strategist=`ux-journey-insight`, structure-validator=`proposal-structure-validation`, slide-builder=`proposal-slide-builder`. 스킬이 가용하지 않으면 각 agent .md의 폴백 지침대로 수행한다. concept-planner · reference-collector · feedback-integrator · release-packager는 대응 스킬이 없으므로 agent .md의 절차대로 직접 수행한다. 스킬 산출물이 agent .md의 출력 서식(제안 키워드 · 페이지별 삽입내용 등)을 채우지 못하면 agent .md 기준으로 덧붙인다.
   - **모델 티어링**: 추론(rfp-analyst·ux-strategist·concept-planner·structure-validator·feedback-integrator)=opus, 제작 · 검수(slide-builder·reference-collector·release-packager·qa)=sonnet 권장.

1b. **★ 단계별 입출력 경로 확인 (매 단계 착수 시)**: 각 단계(S1–S7 · qa) 착수 직전에 그 단계가 **참고할 기존자료(입력) 경로**와 **완료 산출물 저장 경로**를 사용자에게 확인한다(기본값 제시 → 다르면 지정받음). input·output은 **프로젝트(Task)별 하위폴더로 분리**한다.
   - 입력 기본값: `input/{프로젝트 폴더}/` (S1) / 직전 단계의 `_workspace/{프로젝트}/` 산출물 (이후 단계) / 피드백 회의록 `input/{프로젝트 폴더}/feedback/r{n}/` (S5)
   - 산출물 기본값: 중간물 `_workspace/{프로젝트}/`(차수 기록은 `r{n}/`), 산출물 `output/output-{프로젝트 폴더}/`
   - `{프로젝트 폴더}` = `YYMMDD. [제안] {사업명}`(드라이브 폴더명과 같게) · `{프로젝트}` = `{클라이언트}-{주제}`. 아래 규칙에 남은 `{slug}` 표기는 이 둘을 가리킨다(input · output = 프로젝트 폴더, _workspace = 프로젝트).
   - 사용자가 경로를 지정하면 그 경로를 정본으로 사용하고, 이후 단계에도 이어 적용한다.

2. **인테이크 — 한 번에 하나씩 순차 질문** (파이프라인 착수 직전): 제안서 작성 요청이 오면 산출물 1줄 선언 후, 필요한 확인 항목을 **한꺼번에 나열하지 말고 하나씩** 묻고 답을 받아 진행한다(콜드 메뉴 금지·추론 가능한 건 안 물음). 순서:
   - ① **클라이언트명 / 사업명 / 업무명** (자료에 있으면 추출해 확인만 · 파일명에 쓸 업무명은 처음 쓰는 것이면 반드시 확인)
   - ② **RFP/입력자료 확정** (`input/{slug}/`의 어떤 파일이 정본인지)
   - ③ **★ 스타일 확인 — HTML 추출 전에 「기본 스타일로 추출할까요?」를 한 번 묻는다.** 기본값은 하우스 스타일(warm paper + near-black ink · 정본 = `../../global-house-style/house-style.css`)이고, **확인을 받은 뒤 추출한다** — 묻지 않고 바로 뽑지 않는다. "기본으로/네/알아서"면 하우스 스타일로 진행. 사용자가 CI 적용을 답하면 그때 CI/BI 컬러 5개를 HEX 로 확정한다(확인 방법 = `references/design-system.md` §2). 과거 산출물·다른 프로젝트의 CI 를 재사용하지 않는다. CI 를 요청받았는데 끝내 확정 못 하면 중립 팔레트를 새로 만들지 말고 하우스 기본값으로 렌더링하고 `[CI 확인 필요]` 표기. **확인 질문 없이 진행되는 경우(질문 생략·무응답·"한 번에 진행" 지시·비대화형 실행)에도 스타일을 임의로 고르거나 추출을 보류하지 않는다** — 이 하네스에 정의된 기본 양식(`template/base_template.html` + `template/slide-tokens.css` = 하우스 스타일)으로 작성한다.
   - ④ **골격** — 경쟁입찰형(기본 · 컨셉 · 스토리 우선) / 견적형(공수 기준). RFP에 평가 항목 · 배점 · 발표가 있으면 경쟁입찰형으로 보고 확인만 한다.
   - ⑤ **대상 범위 · 제출 기한** — 전체 일괄 vs 특정 장. [선택] 장(회사소개·수행실적·유지보수) 포함 여부, 단일안 vs 복수안(1안/2안).
   - 한꺼번에 답하면 수용하고 남은 것만 이어 묻는다. "알아서"면 표준 가정으로 진행.
   - **여기서 묻지 않는 것 — S4 착수 시 「추출 전 확인」에서 순서대로 정한다**(`agents/slide-builder.md` STEP 0): ⓐ **기본양식 확인** — Figma 장표 템플릿 · PPT 마스터가 있는지 묻고, 있으면 열어서 프레임 크기 · 콘텐츠 영역 · 헤더 구조 · 장표 코드 체계를 읽는다. 이어서 **제출 포맷**(「최종 제출본을 HTML 덱으로 제작할까요, 아니면 HTML 은 미리보기이고 PPT/Figma 가 제출본인가요?」 — HTML 최종본이면 소스 혼합 · 피그마 백업 여부까지 확정하고 `references/deck-production-playbook.md` + `template/deck_1600_template.html`로 진행, 답이 없으면 PPT/Figma 제출본으로 가정하고 알림)과 **작업 사이즈**(양식이 있으면 그 규격이 정본 · 없으면 1280×720 / 1600×900 / 1920×1080 / pptx 16:9 / A4 가로 중 확인)를 확정한다. 확정 전에는 골격을 만들지 않고, 모든 슬라이드 · 피그마 백업 프레임 · PDF 페이지가 이 규격 하나를 따른다. ⓑ **전체 볼륨(페이지) 확인** — 목차 GATE ②에서 승인받은 확정 장수를 다시 보이고 확인. ⓒ **삽입 콘텐츠 수집** — Figma 레퍼런스 · 경쟁사/레퍼런스 사이트(`agents/reference-collector.md`). ⓓ **공통지침 읽기** — `references/writing-style.md`.

3. **★ 작업 순서는 항상 컨셉 승인 → 목차 승인 → 추출 전 확인 → 콘텐츠 초안(마크다운) → HTML → PPT/Figma.** 컨셉 승인 없이 목차를 짜지 않고, 콘텐츠 확정 없이 임의로 포맷 파일을 만들지 않는다(`proposal-slide-builder` 원칙). 추출 전 확인에서 **HTML 최종본**으로 확정되면 HTML 이 곧 제출본이므로 변환 단계 대신 `references/deck-production-playbook.md`(취합·편집·검수·피그마 백업·목차 시트)를 따른다.

3-1. **★ 문체 공통지침 (추출 전 필독 · 차수마다 재검토)**: 제안서 문구는 `references/writing-style.md`대로 쓴다(기준 덱 = 메리츠화재 2027 발표본 2026-11-09). 항목 · 설명은 명사구 종결, 「~함 · ~임 · ~음 · ~됨」 금지, AI가 쓴 티가 나는 표현(번역투 연결어 · 근거 없는 형용사 · 상투어) 금지, 합니다체는 고객의 말 · 대비 문장에만, 거버닝 메시지의 약속형(~하겠습니다)은 기본 명사구에 대한 예외로 일부만 허용(사용자 결정 2026-11-10 · 쓴 장은 완료 보고에 코드로 표기). 초안(`04_content.md`)과 덱을 `perl scripts/check_style.pl`로 점검해 [위반] 0건에서 추출한다. 사용자가 확정한 문장은 점검에 걸려도 고치지 않고 보고만 한다.

3-2. **★ 차수 규칙 (2차 추출부터)**: 피드백은 회의록으로 변환된 파일(md · pdf · docx)로 받아 대장(`r{n}/05_feedback.md`)으로 만들고 승인받은 뒤 반영한다. **대장에 없는 장표 · 문구는 손대지 않는다.** 직전 버전은 `old/`에 보관하고 새 버전 파일(+0.1)을 만들며, `perl scripts/diff_deck.pl`로 뽑은 변경분을 근거로 **목차 기준 항목별 변경사항 HTML 간략본을 별도 파일로** 덱과 함께 낸다(`agents/feedback-integrator.md`). 마감 수정처럼 장 · 문구를 직접 지정받으면 지정한 것만 그대로 반영한다(관련 장 검토 · 표기 보정 · 추가 제안 금지).

3-3. **★ 최종본 (S7)**: 제출 포맷(PDF · HTML · PPT) · 기한 · 파일명 · 분리 제출물 · 쪽수 제한 · 발표용 파생본을 확인하고 대상 버전을 동결한 뒤 포맷별로 뽑는다. 제출 전 점검표를 `07_release.md`에 남긴다(`agents/release-packager.md`). 제출 · 발송은 사용자가 한다.

3a. **★ 덱 편집은 스크립트로만**: 페이지 삭제·삽입·교체·재번호는 `scripts/deck_edit.py`, 피그마 장표 벡터 취합은 `scripts/fig2svg.py`, 코드박스 통일은 `scripts/codebox_overlay.py`, 검수 렌더는 `scripts/render_pages.sh`, 목차 시트는 `scripts/deck_toc.py`. 번호·코드를 손으로 고치지 않는다. 실행 전 `_prev.html` 백업이 남는지 확인하고, 빠지는 장표(발표용 iframe 등)는 별도 파일로 보관 후 사용자에게 고지한다.

3c. **★ 내부망 URL 함께 제공 (HTML 산출 완료 시)**: HTML 산출물을 저장·검수한 뒤 완료 보고에 사내망 링크를 같이 준다(2026-10-22 사용자 지시).
   ① `~/Documents/Local-Projects/internal-share/<프로젝트 약칭>/`에 output 원본을 가리키는 심볼릭 링크 2개(원래 파일명 + `index.html`)를 만든다 — 파일 복사 금지.
   ② 비어 있는 포트를 고른다(8001부터 차례로 `lsof -nP -iTCP:<포트> -sTCP:LISTEN` 확인). 서버는 단독 명령으로 띄운다: `nohup python3 -m http.server <포트> --bind 0.0.0.0 --directory <폴더> > <폴더>.log 2>&1 &`
   ③ `127.0.0.1`과 사내 IP(`ipconfig getifaddr en0`)로 200 응답을 확인한다.
   ④ 보고에는 **짧은 주소 `http://<IP>:<포트>/`만** 적는다 — 파일명 인코딩 전체 주소는 쓰지 않는다(2026-10-22 지시). 맥 IP가 DHCP로 바뀔 수 있다는 점을 한 줄 덧붙인다.
   - 같은 프로젝트로 이미 띄운 서버가 있으면 새 서버를 띄우지 않고 심볼릭 링크만 새 파일로 바꾼다.
   - 실행이 막히면 재시도하지 말고 같은 명령을 `!` 한 줄로 드린다. 상세 절차·사용 중 포트 = 메모리 `internal-url-share`.

5a. **★ 외부링크 · 아이콘 (HTML 산출물 공통, 2026-11-10 지시)**: 문서형 HTML(RFP 분석 · 리서치 · 벤치마킹 · 현황)은 출처 인용에만 링크를 걸지 않는다. **본문에 나오는 사이트 · 서비스 · 기관 · 제품 · 도구 이름도 공식 URL이 있으면 링크**한다(예: FunETF · 삼성자산운용 · KODEX · 토스증권 · Playwright · 금융감독원).
   - **마크업은 하나** — `<a class="ext" href="https://…" target="_blank" rel="noopener">텍스트</a>`. 굵은 라벨은 `<b><a class="ext" …>`. 체인 아이콘 `a.ref` 금지.
   - **아이콘 = 텍스트 우측 끝 블랙 라인 아이콘**(Lucide external-link · 선 2.4 · 글자 높이 .8em · `currentColor` · 투명도 없음). 스타일 정본 = `~/.claude/house-style/house-style.css` §22(= `../../global-house-style/house-style.css`) — 산출물 `<style>`에 아이콘 규칙을 따로 덧대지 않는다. hover · focus는 반전 + 아이콘 우상향 1px, 인쇄에서는 아이콘 숨김.
   - **연결 범위**: 섹션(h2) 하나에서 같은 URL은 첫 등장 1회. 같은 섹션에 그 이름을 담은 링크가 이미 있으면 건너뛴다. `브랜드 + ETF`처럼 이어진 이름은 전체에 걸어 아이콘이 단어 중간에 끼지 않게 한다(`KODEX ETF ↗` · `삼성자산운용㈜ ↗`). **제외**: 제목(h1–h6) · 표지 · 토프바 · LNB · 목차 · 거버닝 문장(`.concept` · `.closing`) · 코드 · 출처 표 · 존재하지 않는 도메인(RFP 오기재 등) · 내부 실적 고객사 나열.
   - **URL 검증**: 걸기 전에 전부 열리는지 확인한다(200, 봇 차단 403은 사이트 존재만 확인). 로그인 벽으로 보내거나 다른 서비스로 바뀐 주소는 쓰지 않는다. 조회에는 공개 도메인만 쓰고 RFP 입찰 조건은 검색어에 싣지 않는다.
   - **검수**: ① 링크 전후 화면 텍스트 동일 ② 중첩 `<a>` 0 · 태그 균형 ③ 새 링크의 `target` · `rel` · `https` ④ 대표 절을 렌더해 아이콘이 우측 끝 · 블랙인지 확인. 기존 파일에 소급 적용할 때는 쓰기 직전에 다른 세션이 그 파일을 고치지 않았는지(md5) 다시 확인한다.
   - **출처 표**에는 증거로 인용한 URL만 둔다(고유명사 바로가기 링크는 넣지 않는다). 슬라이드 골격(`template/base_template.html`)에는 §22가 없으므로, 덱에 외부링크를 넣을 때는 정본 §22 블록을 덱 `<style>`에 그대로 복제한다.
