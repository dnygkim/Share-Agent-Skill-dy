# ORCHESTRATOR — 제안서 작업 7단계 파이프라인

> 이 하네스는 `.claude/`가 아닌 일반 폴더라 **자동 트리거되지 않는다.** 메인 에이전트(나)가 이 문서를 읽고 직접 실행한다: 각 단계에서 해당 역할 정의(`agents/*.md`)를 따라, **대응 스킬을 `Skill` 도구로 호출**하거나(우선) 그 문서의 절차 · 폴백 지침대로 수행한다.
> **파이프라인의 정본은 이 문서다.** `CLAUDE.md`는 동작 규칙, `README.md`는 개요만 둔다 — 단계 · 파일명 · 게이트가 어긋나면 이 문서를 따른다.

## 실행 모드
**컨셉 먼저, 차수 반복.** 제안서는 대부분 경쟁입찰이므로 컨셉 · 스토리를 승인받은 뒤 목차를 짜고, 1차 추출 → 임원 피드백 → 2차 추출을 차수로 되풀이한 다음 최종본으로 닫는다.

```
S1 분석 · 리서치 ─▶ S2 컨셉 · 스토리 ─[GATE ①]─▶ S3 목차 ─[GATE ②]─▶ S4 1차 추출 ─▶ qa
 01_rfp(+01_ux)      02_concept                    03_structure          04_content · 04_refs · 덱 v0.1
                                                                              │
        ┌─────────────────────────────────────────────────────────────────────┘
        ▼
S5 피드백 대장 ─[GATE ③]─▶ S6 n차 추출 + 변경분 HTML ─▶ qa ─┐      (S5–S6 = 차수마다 반복)
 r{n}/05_feedback           덱 v0.n · r{n}/06_changes        │
        ▲────────────────── 추가 피드백 ────────────────────┘
                                                             ▼
                                              S7 최종본 (제출 포맷 · 제출 전 점검)
                                               07_release · 제출본 v1.0
```

- **골격은 둘**: 경쟁입찰형(기본 · `references/skeleton-bid.md`)과 견적형(공수 기준 · `references/section-prompts.md`). RFP에 평가 항목 · 배점 · 발표가 있으면 경쟁입찰형이다. 견적형이면 S2를 「제안 방향 3가지」 한 쪽으로 줄이고 GATE ①을 GATE ②와 묶는다.
- **qa는 단계가 아니라 추출마다 붙는 검수**다(S4 · S6 · S7 뒤). FAIL이면 보정 후 재검수.
- **Dan Jr. 등급 조회**: 게이트 · 인테이크 질문 직전에 `~/.claude/persona/persona.md`를 본다(A 진행 · B 진행 후 보고 · C 질문). GATE ①②③은 persona.md에 없는 결정이므로 그대로 승인을 받는다.
- 모델: 추론 단계(S1 · S2 · S3 · S5)는 opus, 제작 · 검수(S4 · S6 · S7)는 sonnet 권장. 각 에이전트는 자기 .md의 「참조 파일」만 읽는다.

## Phase 0 — 컨텍스트 확인 (시작 시 반드시)
- **프로젝트별 폴더 분리** — 입력 · 중간물 · 산출물을 프로젝트마다 나눈다.

  | 용도 | 경로 | 예 |
  |---|---|---|
  | 입력 자료 | `input/{프로젝트 폴더}/` | `input/261110. [제안] 교보자산운용 홈페이지 재구축/` |
  | 피드백 원문 | `input/{프로젝트 폴더}/feedback/r{n}/` | 회의록 md · pdf · docx |
  | 중간물 | `_workspace/{프로젝트}/` | `_workspace/교보자산운용-홈페이지재구축/` |
  | 산출물 | `output/output-{프로젝트 폴더}/` | `output/output-261110. [제안] 교보자산운용 홈페이지 재구축/` |

  - `{프로젝트 폴더}` = `YYMMDD. [제안] {사업명}`(드라이브 폴더명과 같게), `{프로젝트}` = `{클라이언트}-{주제}`(공백 없이).
  - 산출물은 드라이브 `02. Work` 산출물 경로에도 같은 파일로 둔다(Dan Jr. W-13). `input/` · `output/` · `_workspace/`의 클라이언트 자료는 커밋하지 않는다.
- **어느 단계에서 시작하는지 판정** — `_workspace/{프로젝트}/` 상태와 요청으로 정한다.

  | 상태 · 요청 | 시작 단계 |
  |---|---|
  | 비어 있음 | S1 |
  | `01_rfp.md`만 있음 | S2 (컨셉) |
  | `02_concept.md` 승인됨 | S3 |
  | `03_structure.md` 승인됨 | S4 |
  | 덱 있음 + 회의록 · 피드백 제공 | S5 → S6 (차수 +1) |
  | 덱 있음 + 「제출본 뽑아줘 · PDF로」 | S7 |
  | 덱 있음 + 장 · 문구 직접 지정 | 지정한 것만 수정(대장 생략) → 변경분 데이터로 범위 확인 |
  | 특정 섹션 단독 요청(「표지만」) | slide-builder만 |
  | 같은 프로젝트에 새 RFP · 범위 변경 | 기존 `_workspace/{프로젝트}/`를 `{프로젝트}_prev/`로 옮기고 S1 |

- 앞 단계 산출물 없이 뒤 단계를 요청받으면(컨셉 없이 「목차 짜줘」) 빠진 단계를 한 줄로 알리고, 그 단계를 짧게 먼저 할지 사용자가 준 내용으로 대신할지 묻는다.

## ★ 시각 표시 (시작 · 완료)
- 착수 시: 현재 시각 조회(`date +"%H:%M"` 또는 `Get-Date -Format "HH:mm"`)해 `현재 HH시 MM분입니다. 작업 시작합니다.`
- 완료 시: `현재 HH시 MM분입니다. 작업 완료했습니다.` (시:분은 반드시 조회, 추정 금지)
- 완료 보고에는 HTML 산출물의 **내부망 URL**을 짧은 주소로 함께 적는다 — 절차 = `CLAUDE.md` 3c

## Phase 1 — 입력 수집 + 인테이크
- **입력 인벤토리(자료 > 유추)**: 받은 자료(RFP · 기능목록 · 구성도 · 사이트 · 기존 제안서)를 영역 × 출처(자료 제공 / 부분 / 없음)로 매핑한다. 자료가 있는 영역은 자료가 정본이다.
- **인테이크 — 한 번에 하나씩**(추론 가능한 것은 확인만):
  ① 클라이언트명 · 사업명 · **업무명**(파일명에 쓸 이름 — 처음 쓰는 업무명은 반드시 확인) → ② 입력 자료 정본 확정 → ③ **골격**(경쟁입찰형 기본 / 견적형) → ④ **스타일 = 고객사 로고 Primary 기본**(대표 사이트 · 로고 확인 → **미확인 · 후보 복수면 먼저 묻기** → Primary 실측 → 추출 전 「CI Primary `#HEX`(출처)로 추출할까요?」 한 줄 확인 · 무확인 진행 시 확정분은 CI, 미확인은 하우스 기본 + `[CI 확인 필요]` · 보류 금지 · 정본 `references/rfp-report-format.md` §2) → ⑤ 대상 범위(전체 / 특정 장) · 제출 기한.
- **제출 포맷 · 기본양식 · 작업 사이즈 · 분량은 여기서 묻지 않는다.** 분량은 GATE ②에서, 나머지는 S4 착수 시 「추출 전 확인」에서 정한다.

## 단계별 실행 — `{ws}` = `_workspace/{프로젝트}/`

### S1 — RFP 분석 · 동종/유사 업계 리서치 (`agents/rfp-analyst.md`)
- 요건을 구조화하고 산업 · 경쟁사 · 동종/유사 업계 사례를 리서치한다. 결과의 머리에 **제안 주요 키워드 5–7개**와 **제안 방향성 후보 2–3안**을 둔다 — S2의 재료다.
- 구축 · 리뉴얼처럼 화면 · 여정이 본론인 사업이면 `ux-strategist`를 선택 모듈로 돌려 `01_ux.md`(여정 · IA 인사이트)를 더한다. 운영 · 유지보수 사업은 생략한다.
- 사용자에게 보일 분석 보고서(HTML)는 이 단계에서 만든다 — 양식 · 구성(PART Ⅰ RFP 분석 · Ⅱ 현황 · 시장 · Ⅲ 중점 과제 심층 · Ⅳ 제안 전략 · 실행 초안) · 기본 그래프 · 고객사 CI Primary 적용은 `references/rfp-report-format.md` + `template/rfp_report_template.html`(기준본 = 삼성자산운용 FunETF v0.3 · 2026-11-11). 대표 사이트 · 로고를 확인하지 못하면 추출 전에 먼저 묻는다.

### S2 — 제안 컨셉 · 스토리텔링 (`agents/concept-planner.md`) → GATE ①
- 과제 3–5개 → 컨셉 후보 2–3안 → 추천안의 스토리 흐름(9단계) → 표지 · 2장 · 맺음의 거버닝 메시지 후보.
- **승인 전에는 목차를 짜지 않는다.** 이후 컨셉이 바뀌면 `02_concept.md`를 먼저 고친다.

### S3 — 제안 목차 (`agents/structure-validator.md`) → GATE ②
- 컨셉 · 스토리를 장으로 나눈다. 목차 표의 행 = 장표 1장이고, **「페이지별 주요 삽입내용」 열**(핵심 메시지 · 들어갈 도표/수치 · 근거 출처 · 필요한 레퍼런스)을 반드시 채운다.
- RFP 요구 항목 ↔ 장표 대응을 검증하고, **확정 장수**(본문 · 별첨 · 발표 범위)를 머리에 적는다.
- 승인 전에는 본문을 만들지 않는다.

### S4 — 제안서 초안 · 1차 추출 (`agents/slide-builder.md`)
순서를 지킨다.
1. **기본양식 확인** — Figma · PPT 양식 파일이 있는지 묻고, 있으면 열어서 프레임 크기 · 콘텐츠 영역 · 헤더 구조 · 장표 코드 체계를 읽는다. 제출 포맷(HTML 최종본 / PPT · Figma 제출본)과 작업 사이즈를 함께 확정한다.
2. **전체 볼륨 확인** — `03_structure.md`의 확정 장수를 다시 보이고 확인받는다(양식을 보고 장수가 달라지면 여기서 고친다).
3. **삽입 콘텐츠 수집** — `agents/reference-collector.md`: Figma 레퍼런스 · 경쟁사/레퍼런스 사이트 · 실적 자료 → `04_refs.md`.
4. **추출** — 콘텐츠 초안(`04_content.md`) → 사용자 확정 → HTML → (제출 포맷에 따라) PPT/Figma 변환 또는 HTML 최종본 취합 루틴(`references/deck-production-playbook.md`).
5. **공통지침 적용** — `references/writing-style.md`를 읽고 쓴다. `perl scripts/check_style.pl`로 초안과 덱을 각각 점검해 [위반] 0건.
6. **장표 품질 기준** — `references/slide-quality-bar.md`로 덱 유형(§1)을 정하고, 장표마다 유형별 「반드시」(§3)로 자기검증한다. qa는 §5 완성도 점검표로 검수한다.
- 산출: 덱 **v0.1** → qa → `r1/qa.md`.

### S5 — 피드백 반영 (`agents/feedback-integrator.md`) → GATE ③
- 입력 = 회의록으로 변환된 파일(md · pdf · docx). 발언 단위로 쪼개 대상 장표 · 유형 · 처리 방안을 붙인 **피드백 대장**을 만든다.
- 상충 · 상위 변경(컨셉 · 목차) · 분량 증감을 찾아 표시하고, 「확인 필요」와 「상충」만 한 번에 묻는다. 승인 전에는 덱을 고치지 않는다.

### S6 — 제안서 2차(n차) 추출 (`agents/slide-builder.md` + `agents/feedback-integrator.md`)
1. 공통지침 재검토(`writing-style.md` §7 · 문체 지적 반영).
2. 직전본을 `old/`에 보관하고, 대장의 「반영」 항목만 반영한 새 버전을 만든다(버전 +0.1 · 그날 날짜).
3. `perl scripts/diff_deck.pl <직전본> <신규본> --md {ws}/r{n}/06_changes.md --json …` → 대장과 대조(의도하지 않은 변경 · 미반영 확인).
4. **변경분 HTML 간략본**을 별도 파일로 만든다 — 목차 기준 항목별 변경사항. 2차 추출부터 덱과 항상 한 쌍으로 전달한다.
5. qa → `r{n}/qa.md`. 추가 피드백이 오면 S5로 돌아가 차수를 올린다.

### S7 — 제안서 최종본 (`agents/release-packager.md`)
- 제출 조건(포맷 · 기한 · 파일명 · 분리 제출물 · 쪽수 · 발표용 파생본)을 확인하고 대상 버전을 동결한다.
- 포맷별 추출(PDF · HTML · PPT) → 제출 전 점검표 → `07_release.md`. 동결 뒤 수정은 지정한 장 · 문구만.

| `07_release.md` | S7 | 제출 조건 · 점검표 · 파일 목록 |

**산출물** — `output/output-{프로젝트 폴더}/` 아래. 파일명은 전역 규칙(`업무명-문서명-버전-작성일자`)을 따른다.

| 산출물 | 파일명 예 |
|---|---|
| 분석 보고서 | `교보자산운용리뉴얼제안-RFP요약-v0.2-20261110.html` |
| 제안서 덱 | `교보자산운용리뉴얼제안-제안서-v0.1-20261117.html` |
| 변경분 간략본 | `교보자산운용리뉴얼제안-제안서변경분(2차)-v0.1-20261120.html` |
| 제출본 | RFP 지정 > 사용자 지정 > `…-제안서-v1.0-YYYYMMDD.{pdf\|html\|pptx}` |

- 부산물 폴더: `old/`(직전 버전 · `_prev.html` · 분리 보관한 iframe 섹션) · `refs/`(수집 이미지) · `render/`(검수 PNG) · `toc/`(목차 시트 매핑) · `submit/`(제출본) · `research/`(리서치 노트).

## ★ 차수와 버전

| 시점 | 버전 | 비고 |
|---|---|---|
| 1차 추출 | v0.1 | `r1/` |
| n차 추출(피드백 반영) | 직전 +0.1 (v0.8 초과 금지) | `r{n}/` · 변경분 HTML 동반 |
| PM 검토 · 지적 반영 완료 | v0.9 | |
| 고객 제출본 | v1.0 | 이후 덮어쓰지 않고 새 버전 파일 |

- 차수가 바뀌면 **새 파일**을 만들고 직전 버전은 `old/`로 옮겨 그대로 둔다(변경분 비교의 기준). 같은 차수 안의 오탈자 · 링크 수정은 파일명 · 버전을 유지한 제자리 갱신이다.
- HTML을 저장할 때마다 `<head>` 수정 이력 메타에 한 줄을 더한다(전역 규칙).
- 장표 코드는 차수가 바뀌어도 유지한다. 새 장표는 그 장에서 쓰지 않은 다음 번호를 받는다.

## 데이터 전달 프로토콜
- **파일 기반(주)**: 위 네이밍 표준. 단계 사이 전달은 파일로 하고, 중간본을 지우지 않는다.
- 서브에이전트 · 스킬 결과는 메인에게 반환 → 메인이 다음 단계로 전달한다.
- 승인 상태는 각 파일 머리의 「상태: … / 승인(YYYY-MM-DD)」 줄로 남긴다 — 다음 세션이 어느 게이트까지 지났는지 이 줄로 판정한다.

## 에러 핸들링
- 단계 실패 1회 재시도. 재실패 시 해당 산출물 없이 진행하되 최종 보고에 **누락 명시**.
- 스킬 미가용 → 해당 agent .md의 폴백 지침으로 수행하고 「스킬 미연결, 폴백 진행」 한 줄 보고.
- 사이트 접근 차단 → 접근 가능 범위만 추출 + 미접근 영역 명시(임의 추정 금지).
- 공수 ↔ 일정 불일치 → 숨기지 말고 표면화 + 어느 쪽이 정본인지 사용자 확인.
- 피드백 상충 → 임의로 고르지 않고 GATE ③에서 묻는다.
- 변경분에 대장 근거가 없는 장표가 나옴 → 되돌리거나 사유를 적고 보고한다.
- CI · 미검증 충돌 데이터 삭제 금지(출처 병기).
