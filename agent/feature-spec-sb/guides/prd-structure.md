> **Owner** 황다혜 프로 · **Resource** https://github.com/starryetribe-droid/AX-Pilot/tree/main
> 원본 가이드의 PRD 작성 규칙을 이 리포에서 오프라인으로 쓸 수 있게 정리한 것이다.
> 서버 토큰이 있으면 `fetch_guide.py`가 서버 최신본을 우선 사용한다.

`SKILL.md` §3 PRD 모드의 Step 3에서 이 문서를 따른다.
입력은 기능 ID(예: `A-02`) 또는 기능명이고, 출력은 아래 9개 섹션이 모두 담긴 `.md` 파일 하나다.
기능 ID로 기능명·카테고리를 찾을 때는 `features-list.md`를 본다.

## 1. 9개 섹션 구조

이 순서대로 쓴다. 필수 섹션은 생략할 수 없다.

| 순서 | 섹션 | 필수 | 역할 |
|---|---|---|---|
| 1 | 개요 | 필수 | 기능 요약 정보 |
| 2 | 선행 조건 | 필수 | 플로우 시작 전 충족 조건 |
| 3 | 플로우차트 | 필수 | Mermaid 플로우 (작성 규칙은 `flowchart-rules.md`) |
| 4 | 단계별 상세 | 필수 | 플로우차트 노드를 표로 전개 |
| 5 | 예외 처리 | 필수 | 비정상 케이스와 사용자 안내 문구 |
| 6 | 화면별 UI 요소 | 권장 | 화면 단위 Input/Button/Checkbox 스펙 |

| 8 | 연관 기능 | 권장 | 다른 기능과의 의존 관계 |
| 9 | 변경 이력 | 필수 | 문서 수정 내역 |

## 2. 섹션별 작성 규칙

### §1 개요

```markdown
## 개요

- 설명: {기능을 한 줄로 요약}
- 우선순위: {P0 필수 | P1 권장 | P2 선택}
- 관련 화면: {이 프로세스에 포함되는 화면 목록, 쉼표 구분}
```

- 설명은 30자 이내.
- 우선순위는 `features-list.md`의 값과 일치시킨다.
- 관련 화면은 플로우에 등장하는 모든 화면을 나열한다.
- 프로젝트 고유 메타(인증 방식, 버전, 담당자 등)가 있으면 항목을 추가한다.

### §2 선행 조건

"시작" 노드에 진입하기 위해 충족돼야 하는 조건을 나열한다.
**사용자 측 조건**(로그인 상태, SMS 수신 가능)과 **시스템 측 조건**(API 정상, DB 접근 가능)을 구분하고,
조건이 충족되지 않을 때 어떻게 되는지도 함께 적는다.

### §3 플로우차트

`flowchart-rules.md`의 6도형·화살표·색상 규칙으로 Mermaid를 작성해 본문에 넣는다.
`SKILL.md` §3 Step 2.5에서 **사용자 승인을 받은 Mermaid를 그대로** 사용한다 — 여기서 새로 그리지 않는다.

### §4 단계별 상세

```markdown
## 단계별 상세

### {n}단계: {단계명}

| 단계 | 도형 | 설명 | 비고 |
|------|------|------|------|
| {번호} | {도형} | {동작} | {부가 정보} |
```

- **단계**: 순서 번호. 분기 하위는 `5-1`, `5-1a` 형태.
- **도형**: 시작 / 처리 / 분기 / 외부 시스템 / 에러 / 종료 중 하나.
  **1도형 1동작** — 두 동작을 한 도형에 넣지 않는다.
- **설명**: 이 단계에서 일어나는 동작을 한 줄로.
- **비고**: 유효성 규칙·API 스펙·조건값·제한시간 등 개발자에게 넘길 구체 정보.

분기 표기:
- 분기에서 나가는 **모든 경로에 Yes/No 또는 조건값**을 표기한다.
- Yes·No 경로 **모두 종료 노드까지** 이어져야 한다.
- 분기 하위는 `단계번호-분기번호` (예: 5 → 5-1 → 5-1a, 5-1b).

전체 플로우가 8단계 이상이면 `### n단계: 이름` 소제목으로 논리 단위를 묶는다.
각 묶음은 하나의 완결된 소프로세스여야 한다 (예: 1단계 SMS 인증 / 2단계 회원 여부 확인 / 3단계 약관 동의).

### §5 예외 처리

```markdown
| 예외 상황 | 처리 방법 | 사용자 안내 |
|----------|----------|------------|
| {상황} | {시스템 반응} | {실제 표시 문구} |
```

- **예외 상황**: 발생 원인을 구체적으로 ("SMS 발송 실패", "인증번호 3회 연속 실패").
- **처리 방법**: 시스템이 어떻게 반응하는지 ("재발송 버튼 활성화", "계정 잠금 30분").
- **사용자 안내**: 화면에 표시할 **완성된 문장**을 큰따옴표로. 개발자가 그대로 코드에 넣을 수 있어야 한다.

아래 5가지 예외 유형을 빠짐없이 포함한다.

1. 사용자 입력 오류 — 유효성 실패, 중복, 형식 불일치
2. 시스템 오류 — DB 실패, 서버 오류
3. 외부 연동 실패 — API 타임아웃, 응답 오류
4. 시간 초과 — 인증 만료, 세션 만료
5. 횟수 제한 초과 — 로그인 실패, 인증 실패

안내 문구 작성 규칙:
- 존댓말(~합니다, ~해주세요)로 쓴다.
- **원인 + 해결 방법**을 한 문장에 담는다.
  좋은 예 "인증 횟수를 초과했습니다. 30분 후 다시 시도해주세요." / 나쁜 예 "오류가 발생했습니다."
- 기술 용어를 쓰지 않는다.
  좋은 예 "일시적인 오류가 발생했습니다." / 나쁜 예 "DB 연결 타임아웃이 발생했습니다."

### §6 화면별 UI 요소

```markdown
## 화면별 UI 요소

### {화면명}

| 요소 | 타입 | 필수 | 설명 |
|------|------|------|------|
| {라벨명} | {타입} | {Y/N/-} | {입력 규칙, 동작 조건} |
```

타입은 아래에서 고르고, 괄호 안의 내용을 설명 칸에 반드시 적는다.

| 타입 | 설명 칸에 명시할 것 |
|---|---|
| Input (text) | 글자 수, 허용 문자 |
| Input (tel) | 자릿수, 자동 포맷 |
| Input (email) | 형식 검증 규칙 |
| Input (number) | 자릿수 |
| Input (date) | 형식(YYYY-MM-DD), 범위 제한 |
| Input (password) | 복잡도 규칙 |
| Textarea | 최소/최대 글자 수 |
| Checkbox | — (단일 동의/선택) |
| Checkbox Group | 최소 선택 수 |
| Radio Group | 기본 선택값 |
| Select | 선택지 목록 또는 "API 호출" |
| Button | **활성화/비활성화 조건 반드시** |
| Toggle | 기본값 |
| File Upload | 허용 확장자, 용량 제한 |

- **필수**: Y(필수) / N(선택) / -(해당없음, 예: 전체 동의 체크박스)
- 화면별로 `### 화면명` 소제목을 나눈다. 화면 단위는 **Figma 프레임 또는 URL 경로와 1:1**이어야 한다.
- 조건부 노출 요소는 설명에 "~시 노출" 형태로 조건을 적는다.

### §7 데이터 처리

**수집 항목**

```markdown
| 항목 | 수집 시점 | 필수 | 보유 기간 |
|------|----------|------|----------|
```

- 이 프로세스에서 수집하는 모든 개인정보·데이터를 나열한다.
- 수집 시점은 §4의 단계명 또는 §6의 화면명과 매핑한다.
- 보유 기간은 **법적 근거와 함께** 적는다.
  - 전자상거래법 — 계약·청약철회 5년, 대금결제 5년, 소비자 불만 3년
  - 통신비밀보호법 — 통신사실확인자료 3개월
  - 개인정보보호법 — 목적 달성 시 즉시 파기
  - 서비스 정책 — "회원 탈퇴 후 30일" 등
- 선택 항목은 미입력 시 기본값을 비고에 적는다.

**DB 저장**

```markdown
| 컬럼 | 타입 | 설명 |
|------|------|------|
```

- 컬럼명은 영문 snake_case (`user_id`, `birth_date`, `marketing_agreed`). PK는 항상 첫 행.
- 타입은 `VARCHAR(n)` / `TEXT` / `INT`·`BIGINT` / `DECIMAL(p,s)` / `BOOLEAN` / `DATE` / `DATETIME` / `ENUM('a','b')` / `JSON` 중에서 고르고, 제약조건(`PK`, `UNIQUE`, `FK`, `NOT NULL`, `DEFAULT`)을 뒤에 붙인다.
  예: `VARCHAR(36) PK`, `VARCHAR(11) UNIQUE`, `BOOLEAN DEFAULT FALSE`
- **모든 테이블에 `created_at`·`updated_at`(DATETIME)을 포함**한다.
- PK는 UUID v4(`VARCHAR(36)`) 또는 Auto Increment(`BIGINT`).
- 기존 테이블에 컬럼을 추가하는 경우 "기존 테이블: {테이블명}"으로 표기한다.
- 동의/비동의 같은 이력성 데이터는 DATETIME으로 **동의 시점**을 저장한다.
- 복수 선택 데이터(채널 목록 등)는 JSON 타입을 쓴다.

### §8 연관 기능

```markdown

|---------|--------|----------|
```

`features-list.md`의 기능 중 이 프로세스와 연관되는 것을 나열한다.
연관 시점은 구체적으로 — 좋은 예 "로그인 페이지에서 소셜 로그인 버튼 함께 노출" / 나쁜 예 "관련 있음".
연관 유형: 선행 관계 · 후행 관계 · 동시 노출 · 데이터 공유 · 화면 공유.

## 3. 플로우 분석 시 반드시 확인할 것

프로세스를 분석할 때 아래 분기가 빠지지 않았는지 점검하고, 누락을 발견하면 §4에 추가한 뒤 §9에 기록한다.

- 모든 사용자 입력에 유효성 검사 분기가 있는가?
- 모든 외부 시스템 호출에 실패 분기가 있는가?
- 모든 분기의 Yes/No 경로가 종료까지 이어지는가?
- 선택 항목 미입력·미동의 시 스킵 분기가 있는가?
- 횟수 제한이 필요한 동작에 제한 초과 분기가 있는가?

| 상태/에러 페이지 (Status/Error) | G-01 | 404/500/네트워크/세션만료/권한없음 각각의 안내, 복귀 동선, 에러 코드 표시 |

분류 원칙:
- 한 화면이 여러 타입에 해당하면(예: 목록 + 검색) **모든 타입의 체크리스트를 적용**한다.
- 17종에 없는 화면은 "기타"로 두고 가장 유사한 타입을 참고한다.

### 자동 적용 가능한 ETRIBE 공통 패턴

누락 항목 중 아래는 사용자가 "패턴 따라가자"라고 답하면 자동 적용한다.

- 목록형 정렬 — "고정 우선 → 작성일 DESC"
- 목록형 페이지네이션 — "10건/페이지, 이전·다음·번호 버튼"
- 목록형 빈 상태 — "{화면명} 항목이 없습니다."
- 폼형 취소 확인 — "작성을 취소하시겠습니까? 입력 내용이 저장되지 않습니다."
- 모달 닫기 — "X 버튼 + 배경 클릭 + ESC 키"
- 상태/에러 페이지 — G-01 매핑

**비즈니스 결정이 필요한 항목**(필터 종류, 권한 정책, 임시저장 지원 여부 등)은 자동 적용하지 않고 반드시 사용자에게 묻는다.
