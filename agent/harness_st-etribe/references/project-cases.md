# 프로젝트 케이스 매트릭스 (착수 시 판별 — analyst 필수)

분석 착수 시 **이 프로젝트가 어떤 케이스인지 먼저 판별**한다. 케이스에 따라 IA 추출·delta 분류·공수 도출이 달라진다. 잘못 판별하면 산출물이 통째로 어긋난다(예: 화면 유지인데 백엔드 신규를 "유지=공수0"으로 오판).

## ★ delta는 2축으로 분류 (핵심)
IA/기능을 RFP 대비 분류할 때 **"표현(화면·디자인·IA)"과 "구현(기능·백엔드·로직)"을 분리**한다. 한 축(화면)으로만 보면 F·G를 놓친다.

| | 표현(화면) 유지 | 표현 변경 | 표현 신규 |
|---|---|---|---|
| **구현 유지** | 그대로(공수≈0) | **디자인만 변경**(디/퍼만·개발0) ← F | 화면 추가(디/퍼) |
| **구현 변경** | 백엔드 보수(개발 부분) | 변경(디/퍼/개 부분) | — |
| **구현 신규** | **화면 유지+백엔드 신규**(개발 신규!) ← G | 변경+신규 | **완전 신규**(디/퍼/개 전체) |

→ 공수 = (표현축 → 디자인/퍼블) + (구현축 → 개발)을 **각각** 본다. "화면이 같으니 유지"라고 개발까지 0으로 깎지 마라(G), "기능 같으니 유지"라고 디자인 변경을 빼지 마라(F).

## 케이스별 처리

| 케이스 | 입력 상태 | IA 처리 | 공수 핵심 |
|--------|----------|---------|-----------|
| **A. IA 확인 불가** | 사이트 접근차단·로그인·자료 없음 | ⏸ 추측 금지 → 사용자에 캡처/계정/메뉴 요청. 못 받으면 `접근불가`+`추정` 플래그, 레퍼런스 역설계 | 추정 전제·confidence↓·데이터갭 명시 |
| **B. 프론트만 확인** | admin 자료 없음 | Front IA 실측 + Admin **유추**(표준 골격, `추정`) 또는 admin 없으면 Front만 | admin 유추분은 밴드·확인 질문 |
| **C. 어드민까지 확인** | 기능목록·메뉴 자료 제공 | **자료 기반**(유추 아님) Front + Admin 2섹션 분리 | 자료 기반 정밀 산정 |
| **D. 어드민만(프론트 없음)** | 백오피스·ERP·관리시스템(공개 프론트 없음) | **Admin(또는 단일) IA만 — Front 섹션 강제하지 마라.** 사용자 화면=운영자용 | 운영 화면·권한·로그·보안이 본체 |
| **E. 리뉴얼/이관** | 현행 사이트/소스 있음 | 현행 IA 전수 → delta(유지/변경/신규) → 관리자 파생 | §1.5 사슬, 인계 전제 |
| **F. 디자인만 변경** | 기능(IA·백엔드) 유지, 디자인 리뉴얼 | IA **구현=유지·표현=변경** | **개발 ≈ 0**, 디자인+퍼블(전 화면 재디자인·반응형). CMS·기능 재구축 금지 |
| **G. 화면 유지 + 백엔드 신규** | 레거시→신규 플랫폼(UI 동일/유사), 기술스택 전환 | IA **표현=유지·구현=신규** | **개발 = 신규(전환)**, 디자인/퍼블은 재사용(절감). 화면 같다고 개발 0으로 깎지 마라 |
| **H. 신규 구축** | 현행 없음 | 레퍼런스·동종·RFP로 IA 역설계, 전부 `추정` | 신규 전체. confidence↓ |

## 판별 후
- analyst는 `01`에 **"프로젝트 케이스 = X (근거)"**를 첫머리에 명시 → architect가 그 케이스의 공수 규칙(2축 delta·인프라 제시·관리자 파생)을 적용.
- 복합 케이스(예: E 리뉴얼 + 일부 G 백엔드 신규)는 영역별로 케이스를 다르게 적용하고 영역 desc에 표기.
- 케이스가 불명확하면 인테이크에서 1개 질문으로 확인(리뉴얼인가/디자인만인가/백엔드 전환인가).
