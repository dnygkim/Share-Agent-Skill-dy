# 공수 산정 방법론 (architect 핵심 두뇌)

> 이 문서는 하네스의 **판단(judgment)** 을 담는다. 다른 레퍼런스가 "어떻게 그리나"(하우스스타일·섹션·정합성)라면, 이 문서는 **"숫자를 어떻게 뽑고 왜 그렇게 뽑나"** 이다. architect가 SSOT(월별 투입표)와 영역별 공수를 만들 때 이 원칙으로 추론한다. qa는 산술만 검증하지만, 잘못된 전제로 뽑힌 숫자는 산술이 맞아도 틀린 견적이므로 — 이 방법론이 1차 방어선이다.

---

## 0. 산정의 출발점 — SSOT(Single Source of Truth)
- **정본은 "월별 투입 인력표"** 다. 영역별 공수·역할매트릭스·WBS·간트·히어로·푸터는 전부 여기서 **파생**된다.
- 사용자가 투입표(이미지/표)를 주면 **그게 무조건 정본**. 나머지를 거기에 맞춰 역산한다. (실제 사례: 웅진 05가 5개월 47.0 → 사용자 제공 6개월 표로 57.0 전면 정합)
- 산정 순서: ① 측정 단위 확정 → ② 영역별 제작공수(디/퍼/개) → ③ 역할·등급·기간 배치(월별표) → ④ 파생표 생성 → ⑤ 정합성 검증.

## 1. 측정 철학 — IA는 페이지(기능) 단위, "스타일 수"는 한 페이지 안의 변형일 때만
가장 자주 틀리는 지점. **IA는 페이지로, 디자인 변형만 스타일로 센다.**

- **★ IA = 페이지/기능 단위로 충실히(1노드=1행).** 상품 상세는 상품이 56개여도 IA에선 **1개 페이지(기능)** 다 — 콘텐츠(상품·게시물) 개수로 페이지 수를 부풀리지 않는다. **IA를 스타일 수로 대체·축약하지 마라**(IA에 "상품상세 5스타일"로 적기 ❌ → IA엔 "상품 상세 1페이지").
- **디자인/퍼블 공수도 화면(페이지) 단위가 기본**(페이지당 1 디자인).
- **★ "스타일 N개"는 같은 기능/페이지인데 표시가 여러 갈래로 다를 때만** 그 페이지에 부속으로 센다. 예) 상품 리스트에 노출되는 상품 상세가 상품 유형별로 레이아웃이 다르면 → **"상품 상세 1페이지 · 디자인 스타일 5"**. 표시가 동일하면 스타일 1(=페이지 1과 같음). 즉 스타일은 IA를 줄이는 도구가 아니라 **한 페이지 내 디자인 변형 수**다.
- 콘텐츠 양(텍스트·이미지 교체)은 **운영/제작 이행 범위**로 분리(디자인/퍼블 공수에서 제외 또는 별도 라인). 예: 상품 소개 이미지 56종 = 배너성 작업(별도) vs 페이지 디자인.
- 하네스 동작: 입력에 "N개 상품/게시물"이 오면 **IA는 기능 페이지 1개로**, 디자인 산정은 **"그 페이지에 표시 변형이 몇 갈래냐(스타일)"**로만 환산하고 근거를 노트에. 개수를 그대로 공수에 곱하지 않는다.
- **IA 이중 카운트 → 공수 연결**(analyst가 `ia_extract.py`로 산출): `page_count`(탭 롤업) = **개발·이관** 단위, `view_count`(탭 포함) = **디자인·퍼블** 단위. 디자인/퍼블은 view_count(화면 단위) 기준이고, **한 페이지 내 표시 변형(스타일 N)이 있을 때만 그 페이지에 가산**(IA page 수는 불변). 분리 페이지를 합치거나 탭을 쪼개면 어긋난다 → IA 충실도가 공수 정확도의 전제.

## 1.5 IA delta → 작업 도출 → 공수 (★ 핵심 추론 사슬 — 산출물의 뼈대)
공수는 **"RFP에 적혔으니 N 포인트"가 아니라, 현행 IA를 RFP 요건 대비 분류한 결과의 함수**다. RFP 포인트를 나열하고 공수로 점프하지 마라 — 아래 사슬을 **명시적으로** 밟는다(이게 산출물에서 "왜 이 공수인지"의 설득력).

1. **현행 IA 전수** (Front + Admin) — site-analyst/analyst가 추출.
2. **RFP 대비 노드별 분류 — ★ 2축(표현/구현)으로**: 각 IA 노드/기능을 **유지 / 변경 / 신규**로 태깅하되, **표현(화면·디자인·IA) 축과 구현(기능·백엔드·로직) 축을 분리**한다. 두 축이 다를 수 있다 — **화면 유지 + 백엔드 신규**(레거시→신규 플랫폼, UI 동일) = 디자인/퍼블 재사용(절감)·**개발 신규**(G, "유지=0"으로 깎지 마라) / **기능 유지 + 디자인 리뉴얼** = 디자인·퍼블 변경·**개발≈0**(F). 케이스 매트릭스는 `references/project-cases.md`.
3. **★ 파생 — 프론트 변경/신규 → 관리자 작업**: 프론트에 콘텐츠/메뉴/기능이 신규·변경되면 **관리자에 대응 작업(콘텐츠 CRUD·노출제어·권한·코드)이 파생**된다. 프론트만 보고 관리자 파생을 빠뜨리지 마라(역도 성립 — 관리자 신규 기능엔 운영 화면이 따른다).
4. **공수 도출(추적 가능)**: 각 영역/기능 공수는 위 분류에서 나온다 — **유지 ≈ 0(재사용)·변경 = 부분·신규 = 전체**. 영역 desc에 **"현행 X → (유지/변경/신규) → Y 작업 → N M/M"** 근거를 남긴다. 유지/변경/신규 비율이 곧 공수 구조(신규 多→개발↑, 유지 多[재스킨]→개발↓).

> 즉 산출물은 **IA 분석 → delta 분류 → (프론트+관리자) 작업 도출 → 공수**가 한 줄기로 흘러야 한다. "RFP 포인트 → 공수" 점프는 빈약 산출물의 징후(실제 사고: GS칼텍스에서 delta·관리자 파생 없이 RFP 포인트만 나열).

## 2. 영역별 제작공수 — 디/퍼/개 3분해
영역(IA 대분류 또는 기능 묶음)마다 `(디 X / 퍼 Y / 개 Z)`로 쪼갠다. 합이 그 영역의 num.

- **디자인(디)**: **화면(페이지) 단위가 기본**, 같은 페이지에 표시 변형이 여럿일 때만 스타일 가산(§1: "상품 상세 1페이지 · 스타일 5"). 공통 디자인 시스템(GUI) + 메인 + 서브 템플릿 + 핵심 비주얼(CI·브랜드).
- **퍼블(퍼)**: 반응형 마크업. 보통 디자인보다 약간 적거나 비슷. 공통/그리드 먼저, 템플릿별 마크업.
- **개발(개)**: **페이지 수가 아니라 "기능·트랜잭션·연동"** 으로 결정 → 4장 참조. 정적 페이지는 개발 0에 가깝다.
- 합산 규칙: 영역 num 합 = 제작 소계(디합/퍼합/개합) = 월별표 직군 소계 = 히어로 분해. (이 사슬은 `consistency-checklist.md`로 강제)

**전형 비율 감(感)** (재스킨형 홈페이지 리뉴얼 기준): 디자인 ≈ 퍼블 ≈ 개발의 1~1.5배, 개발은 기능 의존. 신규 구축/가입 플로우가 끼면 개발이 급증.

## 3. 재스킨 vs 신규 구축 — 개발 공수의 분기
개발 공수는 **"무엇을 다시 만드나"** 로 갈린다. 같은 페이지 수라도 5~10배 차이.

| 모드 | 개발 성격 | 공수 |
|------|----------|------|
| **재스킨(기능 유지)** | 기존 백엔드·CMS·템플릿 유지, 반응형 마크업만 교체 + 필요 폼 추가 | 낮음 |
| **부분 신규** | 일부 모듈 신규 + 나머지 재사용 | 중간 |
| **전면 신규(가입/결제/연동)** | 오케스트레이션·트랜잭션·외부연동·보안 | 높음 |

- **★ "재스킨 4.0" 같은 단일값은 조건부값**이다 — "기존 소스가 정상 인계 + 템플릿/로직 분리형"일 때만 성립. (review-board P0)
  - 레거시(2010년대 JSP, 로직 혼재)면 재스킨이 신규보다 비쌀 수 있다(화면마다 로직 들어내기). → **밴드로 제시**(base ~ 최대) 권장.
- **필수 선결 전제: 기존 소스/CMS/개발환경 인계**(현 운영사 협조). 미인계·품질미흡 시 재산정. 하네스는 이 전제를 **항상 명시**하고, "착수 직후 소스 품질 진단 게이트(1~2주)"를 권고 항목으로 넣는다.

## 4. 개발 공수는 "기능·트랜잭션·연동"으로 — 페이지 수 아님
페이지가 많아도 개발이 작을 수 있고(정적·재스킨), 페이지가 적어도 개발이 클 수 있다(가입 플로우).

- 개발 공수를 키우는 요인: **상태 오케스트레이션**(다단계 가입·이탈복귀·멱등성), **외부연동 직렬결합**(N종), **트랜잭션**(결제·계약), **보안·감사**(금융권), **기간계/레거시 연동**.
- 개발 공수가 작은 것: 정적 콘텐츠 페이지, 게시판(기존 모듈), 단순 폼.
- 사례 대비: 홈페이지 161p 재스킨 개발 ≈ 4 vs 다이렉트 가입 약 26개 화면 개발 ≈ 12~13 (페이지 수와 무관, 트랜잭션·연동 때문).

## 5. 재사용의 비대칭성 — 같은 "재사용"도 절감 폭이 다르다
서브 기능이 호스트 사이트의 자산을 재사용할 때, **무엇을 재사용하느냐에 따라 절감/리스크가 갈린다.** (웅진: 다이렉트가 홈페이지 서브 기능화)

| 재사용 대상 | 효과 | 근거 |
|------------|------|------|
| 화면·UI·상품 콘텐츠 표시 | **확실한 절감** (디/퍼 ↓) | 호스트 디자인·템플릿 그대로 |
| 로그인/회원/세션/개인정보 | **오히려 비용↑ 가능** | 레거시 세션을 금융 가입 플로우(본인인증·결제·전자서명)에 붙이면 세션 보안등급·CI/DI·결제정보 정합성·암호화·접근통제 글루코드 발생. 차라리 독립 세션이 쌀 수도 |

- 하네스 규칙: "재사용=절감"으로 뭉뚱그리지 말고 **디/퍼는 절감, 개발(세션·회원·보안)은 별도 검증·항목화**. 보안·세션·개인정보 정합성은 별도 개발 라인으로 분리(“보안감사 레이어”에 묻지 않는다).
- 미확정 분기: "비회원 가입 후 전환 vs 가입 전 로그인 필수" → 회원연동 공수 ±1.5~2.0 변동 → 고객 확인 전까지 명시.

## 6. 통합 시너지 — 별도 합산보다 줄지만, 선반영은 신중히
여러 건을 한 사이트로 통합하면 공유 자원만큼 준다.

- 공유로 절감되는 것: PM/기획 총괄(1팀), 디자인 시스템(공통 GUI), 퍼블 공통 컴포넌트, 세션·헤더.
- 사례: 다이렉트 단독 개발 13.0 → 통합 시 12.0(-1.0, 공유). 단 5장 비대칭성 때문에 **시너지가 음수(증가)** 가 될 수도 있어 과신 금지.
- **견적 커뮤니케이션 주의(review-board P2)**: 통합 시너지를 견적에 선반영해 깎으면, 미실현 시 손실을 수행사가 떠안는다. → 견적엔 "확인 후 -N 조정" 옵션으로 두거나 밴드로 제시.

## 7. 시스템 경계 & 역할분리표 — 범위 다툼·중복 방지
연동 시스템(기간계·ERP·외부 플랫폼)이 있으면 **무엇이 우리 범위인지** 표로 못 박는다.

- 원칙: 프론트/신규 채널은 "여기까지", 원장(原帳)·라이프사이클은 연동 시스템.
- 사례(기간계 ↔ 다이렉트): 가입·약관·인증·청약·서명·결제승인·가입중 롤백 = 다이렉트 / **결제취소·환불·해약·정산·납입·수금·회계 = 기간계(제외)**. 계약 생성은 다이렉트가 "요청 전달(FEP)", 기간계가 "원장 확정".
- 하네스 동작: 연동 시스템이 입력에 있으면 **역할분리표를 자동 생성**하고, 제외 항목을 "제외 범위" 카드에 명시. 경계가 개발 범위를 한정(=공수 상한)한다.

## 8. 외부연동 & 일정 리스크 — 직렬결합과 의존 일정
- **외부연동 N종이 한 흐름에 직렬로 묶이면** 난도가 곱으로 증가(한 단계 실패 시 복구/재개/멱등성 설계). 연동 수만큼 단순 합산 ❌, 통합·정합성 비용 별도.
- **의존 일정**: 핵심 연동이 외부 일정에 묶이면(예: 기간계 FEP가 신규 ERP TLP 오픈 후 제공) 후반 압축 리스크 → 완화책(선제 완료 6종 + 연계 윈도 분산 + 시니어 보강) + **순연 조항 권고**를 노트에 자동 삽입.
- 연동사 라이선스·심사비·솔루션(전자청약/서명·CMS에디터)은 **구축비와 별도**(제안 후 확정)로 분리 표기.

## 9. 역할·등급 구성 패턴 (월별표 SSOT 작성)
- 직군: **PM/기획 · UI/UX 디자인 · UI/UX 퍼블리싱 · 응용개발** 4군. 각 직군 배경색 고정(house-style).
- 등급: 고급/중급/초급. 월 투입 1.00=풀투입, 0.50=반투입, `-`=미투입.
- **★ 기획 베이스 = 페이지(IA) 수 + 기획-디자인 동반 상승 (필수 — 운영 반복 결함)**: 사이트 작업에서 **기획이 전체 방향성·콘텐츠 수집·화면설계를 담당**한다. 산정 순서:
  - **① 기획 베이스**는 **페이지(IA)·뷰 수에서 1차 결정**(N뷰 화면설계·콘텐츠 정리·구조). **② 난이도·퀄리티(premium·다국어 배수·인터랙션·콘텐츠 신규성)로 기획 추가 공수.** 그 위에 **③ 디자인 공수가 기획 베이스를 기반으로 잡히고, 디자인 난이도로 추가**된다.
  - **★ 디자인 고도화 = 기획도 동반 상승**: 디자인이 어려워지면(premium·다국어·인터랙션) 디자인만 늘리고 기획을 고정하지 마라 — 그 화면의 **콘텐츠 수집·구조 설계·다국어 카피 기획·디자인 QA**가 함께 커진다. **"기획 1명 vs 디자인 3-4명" 식 불균형은 기획 과소의 전형 결함**(실제 사고: GS칼텍스 기획 실무 5.5/1명 vs 디자인 12.5/3명+퍼블 14.0/4명 — 디자인·퍼블 7명을 기획 1명이 받치는 비현실 구성).
  - **점검**: PM 제외 **기획 실무 M/M가 디자인 M/M의 절반에 못 미치거나**, 기획 실무 1명인데 디자인+퍼블 ≥ 4명이면 **기획 과소를 의심**하고 페이지수·난이도 기준으로 재산정(통상 디자인 고도화 사이트는 기획:디자인 M/M가 0.6~1.0 수준). `build_report.py`가 이 불균형을 `[WARN]`으로 탐지.
- 합류/철수 타이밍: 퍼블은 디자인보다 1개월 늦게 합류, 개발 보강 인력은 연계·통합 시점(후반) 합류, 막달(오픈월)은 대개 0.50로 감쇠.
- **★ 인력 투입 연속성 규칙 (0.5 허용 조건 — 필수 준수)**: 한 사람의 투입은 **1.0(풀)이 기본**이다. **0.5(반)는 투입 구간의 "경계 월"(합류 첫 달 ramp-up·철수 막달 ramp-down)에서만** 허용한다.
  - **금지 ① 톱니 패턴**: 연속 투입 인력의 **중간 월을 0.5로 떨어뜨리지 않는다**(`1.0→0.5→1.0` 불가). 한 번 1.0으로 들어오면 빠지기 전까지 1.0을 유지한다 — 사람은 월 중간에 반만 붙였다 떼는 식으로 움직일 수 없다(이것이 "연계 투입 인력은 중간에 0.5 불가"의 의미).
  - **금지 ② 장기 반투입**: 한 인력이 **2개월 이상 연속 0.5**인 패턴은 비현실(반만 일하는 유령 인력)이다 → ⓐ 다른 역할과 한 사람으로 **통합**하거나, ⓑ 더 짧은 기간 **1.0으로 재배치**하거나, ⓒ 진짜 파트타임이면 "자문/검수성 역할(예: PM 일부·QA 입회)"로 **명시**한다.
  - 정당한 0.5: 합류·철수 경계 1개 월 감쇠, 자문/검수(PM 감리·QA 입회), 명시적 파트타임 계획 역할. 그 외엔 1.0 또는 `-`.
  - 예) 안정화 인력을 막 2달 `0.5·0.5`로 까는 대신 → 막달 1개월 `1.0`(또는 기존 개발자가 안정화까지 1.0 연장)으로 재배치하는 것이 정합적.
  - **★ 자동 강제(2026-06-12)**: `build_report.py`가 렌더 시 톱니(중간월 0.5)·장기 반투입(0.5 2개월+ 연속)을 `[WARN]`으로 탐지해 stderr에 출력한다(산술 정합 검사와 별개의 판단 가드). 정당한 파트타임(PM 감리·QA 입회·명시적 파트타임)은 월별표 member에 `"parttime": true`를 달아 예외 처리한다 — 플래그가 없으면 모든 0.5 연속/톱니가 경고된다. qa는 이 WARN을 0으로 만든 뒤 PASS 판정한다.
- 인원 수 = 직군별 행(소계 제외) 개수. 히어로/요약/푸터의 "N명"과 일치해야 함.
- M/M 합 = 행별 월합 = 직군 소계 = 총계. (qa 강제)
- **★ 수행 형태(상주/비상주) — 인테이크 필수 확인, 공수 직접 조정**:
  - **비상주(원격 수행)**: 사내 AI 도구·자동화 활용분을 반영해 **퍼블·개발 공수에 최대 -30% 감면**(난이도·신규성에 따라 0~30% 차등, 적용률·근거를 산정 노트에 명시). **기획·디자인은 고객 협업·콘텐츠 수급 의존**이라 감면 보수적(원칙 미적용).
  - **상주(파견 근무)**: 현장 상주라 AI 활용이 제약 → **감면 미적용**(또는 소폭). **상주 인력(특히 PM)을 매월 0.5로 길게 까는 패턴 금지** — 상주는 현장 풀타임 성격이라 장기 0.5가 비현실이다. 상주 PM은 1.0으로 두거나, 부분 관여라면 "비상주 자문"으로 분리해 구분한다(상주 인력에는 §9 톱니/장기반투입 `parttime` 예외를 주지 않는다).
  - 미응답 시 **상주 가정(감면 미적용)** 으로 보수적 산정 + 데이터갭 명시.
- **★ 예상 인프라 포함 여부 — 인테이크 확인**: 산출물에 기술 아키텍처·AWS 인프라 도식을 넣을지 확인한다. 포함이면 solution-architect가 설계(기본 AWS 형식), 단순 정적/재스킨이라 불필요하면 생략 + 근거 노트. (감면·인프라 모두 비용/스타일이 아니라 **사용자 확인 후 확정**.)
- **★ QA 인력 = 기획자 겸임 (이트라이브 표준)**: **QA 전담 인력을 별도로 잡지 않는다** — QA·UAT는 **기획자(PM/기획 PA)가 겸한다.** 따라서:
  - ⓐ 월별표에 별도 **"QA" 직군/역할 행을 만들지 않는다**(QA 공수는 기획에 포함).
  - ⓑ **기획 인력 중 최소 1명은 QA·UAT·오픈(막달)까지 투입을 유지한다.** 기획이 설계 후 전원 철수해 **막달에 기획 0인 채 통합테스트/UAT가 도는 구성은 불가** — "기획자 없이 QA만 진행"하는 케이스는 없다.
  - ⓒ 역할매트릭스·WBS의 "통합테스트·오픈" 단계 QA 담당 = **기획**(QA 겸)으로 표기.
- **★ 테스트·안정화 구간 인력 감쇠 (막달 ramp-down)**: 막판 통합테스트·UAT·오픈 구간엔 **신규 콘텐츠·신규 제작이 없다.** 따라서:
  - **디자인·퍼블이 2명 이상 투입된 프로젝트는 테스트 구간에 최소 1명씩만 잔류**(수정·대응용), 나머지는 그 전에 철수. 디자이너·퍼블 여러 명이 끝까지 풀투입으로 남는 것 = 과다 산정.
  - **PM·기획·개발은 테스트 구간 풀투입 잔류 가능**(QA·디버깅·실거래 점검·이관 대응).
  - 단 **프로젝트 성격**에 따라 조정: 개발 위주 프로젝트는 개발 막달 풀 유지가 자연스럽고, **디자인 위주 프로젝트는 개발자도 테스트 구간에 감원**할 수 있다. 성격을 보고 ramp-down 대상을 정한다.

## 12. 산정 함정 — 하네스가 선제 방지할 목록 (실전 버그)
1. **"예전 공수 병합"**: 통합본/수정본이 옛 버전의 수치를 물고 옴(웅진 05가 다이렉트 2명/27.0 시절 개발 10.0을 잔류). → **단일 정본 강제, 파생표는 매번 역산**.
2. **부분 수정 후 합계 깨짐**: 셀 1개 고치고 소계·총계·히어로·푸터 누락. → 수정 후 **정합성 사슬 전체 재검증**.
3. **기간 변경의 파급**: 개월수 ±1이면 월별 colspan·매트릭스 단계·WBS 블록·간트(totalWeeks=개월×4, W컬럼)·히어로 기간·푸터 6곳 동시 변경. → 묶음 처리.
4. **측정 단위 부풀리기**: 콘텐츠 수를 그대로 공수화. → 템플릿/스타일 환산 강제.
5. **재사용 일괄 절감**: 세션/회원 재사용까지 절감으로 계산. → 5장 비대칭성 적용.
6. **단일값 과신**: "재스킨 4.0" 등 분산 큰 값을 단정. → 조건부/밴드 명시.
7. **숫자만 맞고 전제 틀림**: qa 산술 통과해도 전제(인계·경계·측정단위)가 틀리면 오답. → architect 단계에서 이 문서로 1차 검토.

## 13. review-board 관점 체크 (제출 전 자가 점검)
큰 견적은 아래를 문서가 방어하는지 확인(미충족 시 노트/리스크 카드에 명시):
- [ ] 기존 소스 인계 **품질 미흡·부분 인계** 분기가 있는가(미인계만 다루지 않았는가)
- [ ] 개발 공수가 **조건부값/밴드**로 제시됐는가(레거시 리스크)
- [ ] **세션·개인정보·보안 정합성**이 별도 항목인가(재사용 뭉뚱그림 아닌가)
- [ ] 회원/세션 통합 방식(비회원→전환 vs 로그인 필수) 분기가 명시됐는가
- [ ] 외부 의존 일정(FEP 등) **순연 조항**이 있는가
- [ ] 비주얼 1순위 화면(메인 등)에 합당한 공수·리비전 한도가 있는가
- [ ] 통합 시너지를 **무리하게 선반영**하지 않았는가
