# ORCHESTRATOR — PRD 생성·갱신 파이프라인

> 이 하네스는 `.claude/`가 아닌 일반 폴더라 **자동 트리거되지 않는다.** 메인 에이전트(나)가 이 문서를 읽고 직접 실행한다. 섹션별 작성 기준의 유일한 정본은 `references/master-prompt-v2.0.md`(이하 "MP")다.

## 실행 모드

```
[신규 생성]
인테이크 → 진단(§2) → 산정단위(§3) ─[GATE 1: 단위 승인]─▶ 범위·R&R·영향도(§4·5·6)
  → 공수(§7) ─[GATE 2: 추천안 승인]─▶ 개요·흐름·총평·리스크(§1·8·9·10) → 자기검증 → output

[업데이트]  ★ 이 하네스의 존재 이유
새 정보 유입 → STATE.md 갱신(레지스터·확정로그) → 영향 섹션 매핑 → 델타 재생성 → 정합 재검증 → 버전업
```

## Phase 0: 모드 판별 (시작 시 반드시)
- **★ 프로젝트(Task)별 폴더 격리**: `input/{slug}/` · `_workspace/{slug}/` · `output/{slug}/`. `slug = {클라이언트}-{주제}` (예: `woongjin-directplatform`).
- `_workspace/{slug}/STATE.md` 상태로 분기:
  - **없음** → 신규 생성 (Phase 1부터)
  - **있음 + 새 자료/답변 유입** → **업데이트 프로토콜** (아래 전용 절 참조)
  - **있음 + 부분 수정 요청**("공수 표만 다시") → 해당 Phase만 재실행 → STATE.md 정합 확인 → output 갱신
  - **있음 + 완전히 새 판 요청** → 기존 `_workspace/{slug}/`를 `{slug}_prev/`로 이동 후 신규 생성

## ★ 시각 표시 (시작·완료)
- 착수: 시각 조회(`Get-Date -Format "HH:mm"`) 후 `현재 HH시 MM분입니다. 작업 시작합니다.`
- 완료: `현재 HH시 MM분입니다. 작업 완료했습니다.` (추정 금지, 반드시 조회)

## Phase 1: 인테이크 + STATE.md 초기화
- **입력 인벤토리(자료 > 유추)**: 받은 자료를 영역×출처(자료제공/부분/없음)로 매핑. 자료 있는 영역은 자료가 정본.
- **인테이크 — 하나씩 순차 질문** (CLAUDE.md §4 순서): ① 클라이언트/사업명 → ② 입력자료 정본 확정 → ③ 프로젝트 유형(MP "유형별 중점 섹션" 표 적용) → ④ AS-IS 실측 가능 여부 → ⑤ 출력 포맷(HTML 기본) → ⑥ (HTML 선택 시) 스타일 확인(CI 컬러 지정 여부).
- 인테이크 완료 즉시 `references/state-template.md`를 복사해 **`_workspace/{slug}/STATE.md` 생성**, 메타 기입. 이후 모든 Phase는 산출과 동시에 STATE.md 해당 절을 갱신한다.

- **★ GATE 1(산정 단위)이 최우선 분기점**: MP 원칙 "단위를 먼저 정의하지 않은 공수는 거품이거나 누락". 단위 승인 전에 공수 숫자를 만들지 않는다.
- **★ GATE 2(추천안)**: 시나리오 A(기본)/B(절감)/C(전수용)/D(추천) 매트릭스로 제시 → 승인된 안의 수치가 STATE.md 공수 정본이 된다. 이후 모든 문서는 이 값만 인용.
- **작성 순서 근거**: MP "v2.0 작성 순서 권장" — §2(실측)→§3(단위)→§7(공수) 확정 후 §1·8·9(서사) 정리. 근거와 서사가 어긋나지 않게 하기 위함.
- **Phase 7 조립**: `{ws}` 산출물을 MP [Output Format Blueprint] 순서(헤더+10섹션)로 조립. HTML이면 MP [HTML 산출물 사양] 준수. 자기검증 8항목 판정표를 문서 말미 첨부.

## ★ 업데이트 프로토콜 (지속 정보 갱신 — 핵심)

새 정보(회의록·고객 답변·추가 실측·범위 변경)가 유입되면 **전체 재생성 금지**, 아래 5단계만 수행:

1. **분류**: 새 자료를 `input/{slug}/{NN}_{유형}_{날짜}/`에 배치하고, 정보를 유형별로 분해 — (a) 기존 Q-xx에 대한 답변 (b) 새 확정 사항 (c) 새 확인 필요 (d) 전제(P-xx) 성립/붕괴 (e) 범위 변경.
2. **STATE.md 선갱신**: 섹션 파일보다 STATE.md를 먼저 고친다.
   - Q-xx 답변 도착 → 상태 `OPEN → ANSWERED`, 답변·출처 기록
   - 확정 사항 → D-xx 신규 등록(날짜·출처·영향 섹션)
   - 전제 붕괴 → P-xx 상태 변경 + **재산정 트리거 발동 여부 판단** (발동 시 Phase 5 재실행 대상)
3. **영향 섹션 매핑**: 각 D/Q/P 항목의 "영향 섹션" 열 기준으로 재생성 대상 `{ws}` 파일을 결정. 예: 단위 변경→02+04, 범위 변경→03+04+05, 답변만→해당 섹션 본문+§10.
4. **델타 재생성**: 영향받는 `{ws}` 파일만 수정 → 처리된 Q-xx는 `ANSWERED → 반영완료`로 승격 → output 재조립.
5. **정합 재검증 + 버전업**: 총 M/M 정합(§0↔7-1↔7-2↔7-5↔STATE) 확인 → `output/{slug}/` 버전업(v0.1→v0.2) → STATE.md 버전 히스토리에 1줄 기록(날짜·트리거·변경 요지·공수 변동).

**버전업 기준**: 정보 유입에 의한 내용 변경 = 마이너 버전업(v0.x). 산정 단위·공수 정본이 바뀌는 재산정 = 사용자에게 고지 후 버전업 + 변경 전후 수치 병기. 오탈자·표현 수정 = in-place.

## 에러 핸들링
- 단계 실패 1회 재시도. 재실패 시 해당 섹션 `[생성 실패]` 표기하고 진행, 최종 보고에 누락 명시.
- 실측 대상 접근 차단 → 접근 가능 범위만 실측 + §2에 미접근 영역 명시(임의 추정 금지, `[착수 후 분석 예정]`).
- 공수 정합 불일치(±10% 초과) → 숨기지 말고 표면화 + 어느 값이 정본인지 사용자 확인 → STATE.md 갱신.
- STATE.md와 섹션 파일 충돌 → STATE.md 승(勝), 섹션 파일 수정.
- 업데이트 중 기존 확정 사항(D-xx)과 모순되는 새 정보 → 삭제 금지, 양쪽 출처 병기 후 사용자에게 판단 요청.
