# qa-master — ISTQB 기반 테스트케이스 생성 · QA 스킬

기획서 · 요구사항정의서 · IA · 플로우차트 · 화면설계서를 넣으면 ISTQB 설계 기법으로 도출한 테스트케이스 엑셀(시나리오 · TC), 기획서 QA 검토 리포트, 테스트 계획서가 나오는 스킬

### 모드 1 테스트케이스 생성

```
① 입력 분석 → ② 범위 확인(조건부 GATE) → ③ 테스트 컨디션 → ④ 기법 · 케이스 설계 → ⑤ 우선순위 → ⑥ 엑셀 생성 → ⑦ 검증 · 보고
```

| <div align="center"><sub>단계</sub></div> | <sub>하는 일</sub> | <sub>사용자 할 일</sub> | <sub>결과물</sub> |
|:---|:---:|:---:|:---:|
| <sub>① 입력 분석</sub> | <sub>입력 문서 전체 읽기 · 테스트 대상 기능 목록 추출 · 모호한 부분 · 모순은 `[확인 필요]` 목록으로 분리</sub> | <sub>문서 첨부</sub> | <sub>기능 목록</sub> |
| <sub>**② 범위 확인 (조건부 GATE)**</sub> | <sub>화면설계서 25페이지 초과 또는 그 외 문서 기능 10개 초과 시 대분류 단위 분할</sub> | <sub>**이번에 만들 범위 선택**</sub> | <sub>생성 범위</sub> |
| <sub>③ 테스트 컨디션</sub> | <sub>상위 컨디션(「화면 X의 기능」) → 상세 컨디션(「입력값 Y가 조건 Z를 벗어나면 거부」) 분해 · 근거 위치 기록</sub> | <sub>—</sub> | <sub>컨디션 목록</sub> |
| <sub>④ 기법 · 케이스 설계</sub> | <sub>기획서 요소 → 기법 매핑(아래 표) · 부정 케이스(경계 밖 · 예외 흐름 · 빈 결과 · 취소 · 중단) 필수 포함 · 기대결과 미정의 시 `[확인 필요]` 병기</sub> | <sub>—</sub> | <sub>시나리오 · TC</sub> |
| <sub>⑤ 우선순위</sub> | <sub>리스크 수준 = 발생 가능성 × 영향 → 상 · 중 · 하 배정 · 기준은 개요 시트에 명시</sub> | <sub>—</sub> | <sub>우선순위</sub> |
| <sub>⑥ 엑셀 생성</sub> | <sub>`scripts/make_tc_excel.py`의 `build_workbook()` 호출 · 실행결과 초기값 `미실행`</sub> | <sub>—</sub> | <sub>TC 엑셀 v0.1</sub> |
| <sub>⑦ 검증 · 보고</sub> | <sub>빈 출처 · 시나리오 ↔ TC 연결 · 기능별 정상/부정 케이스 점검 → 기능별 TC 수 · 적용 기법 · `[확인 필요]` 보고 · 문서 결함 5건 이상이면 모드 2 리포트 제안</sub> | <sub>보고 확인 · 필요 시 `고객 제출용으로 정리해줘`</sub> | <sub>최종 TC 엑셀</sub> |

기획서 요소 → 설계 기법

| <div align="center"><sub>기획서에 이런 요소가 있으면</sub></div> | <sub>적용 기법</sub> |
|:---|:---:|
| <sub>입력 필드(값 범위 · 자릿수 · 형식)</sub> | <sub>동등분할 + 경계값분석(2-value 기본, 리스크 높으면 3-value)</sub> |
| <sub>조건 조합에 따라 결과가 달라지는 규칙(할인 · 권한 · 요금)</sub> | <sub>결정테이블</sub> |
| <sub>상태 · 단계가 변하는 흐름(주문상태 · 회원등급 · 화면 전환)</sub> | <sub>상태전이(최소 0-스위치, 핵심 흐름 1-스위치)</sub> |
| <sub>여러 옵션 · 환경의 조합(브라우저 × OS × 회원유형)</sub> | <sub>페어와이즈 · 분류 트리</sub> |
| <sub>사용자 흐름 · 유스케이스 · 플로우차트</sub> | <sub>시나리오 테스팅(기본 · 대안 · 예외 흐름)</sub> |
| <sub>데이터 생성 · 조회 · 수정 · 삭제가 있는 기능</sub> | <sub>CRUD 테스팅</sub> |
| <sub>명세가 빈약하거나 시간이 부족한 영역</sub> | <sub>탐색적 테스트 차터 + 체크리스트 기반</sub> |

우선순위 기준

- 상(H) = 결제 · 개인정보 · 법적 요건 · 핵심 업무 흐름 · 장애 시 업무가 중단되는 기능
- 중(M) = 주요 기능의 기본 흐름 · 대안 흐름 · 상 · 하 어디에도 해당하지 않는 기능
- 하(L) = 보조 기능 · 표시 문구

화면설계서(PDF/이미지) 입력 — 모드 1 · 2 공통

- 이미지 판독 기본 — 피그마 추출 PDF는 텍스트 추출 시 폰트 인코딩 문제로 글자가 자주 깨져 텍스트 추출은 보조 · PDF 렌더가 안 되는 환경은 PyMuPDF로 페이지별 PNG(가로 1600~2000px) 변환
- 페이지 수 먼저 확인 · 25페이지 초과 시 대분류 단위 범위 확인
- PC/모바일 채널 중복 페이지 = 헤더(Channel · 화면 ID)로 판단 후 차이점만 확인 · 기능 TC를 채널별로 복제하지 않고 채널 차이는 환경/호환 TC로 통합
- 화면 단위 테스트 컨디션 표(화면 ID · 입력 필드 · 버튼 · 상태 · 분기 · 이동 경로)
- 화면에 정의가 없는 값(입력 제한값 · 오류 문구 · 빈 결과 처리) = `[확인 필요]` · 출처 표기 `화면설계서 p.N (화면ID)`

- 심각도: 상 = 구현 시 장애 · 재작업 유발 / 중 = 해석 차이 발생 가능 / 하 = 표현 · 표기 개선

### 모드 1 TC 엑셀 (시트 3개)

| <div align="center"><sub>시트</sub></div> | <sub>구성</sub> |
|:---|:---:|
| <sub>개요</sub> | <sub>세로 2열(항목/내용) — 프로젝트명 · 대상 문서(테스트 베이시스) · 테스트 범위 · 적용 기법 요약 · 우선순위 기준 · 총 시나리오/TC 수 · 작성일/작성 도구 · 확인 필요 사항 · 대분류 약어 대응표</sub> |
| <sub>테스트 시나리오</sub> | <sub>시나리오 ID(`TS-<대분류약어>-<3자리>`, 예 `TS-LGN-001`) · 구분(대분류) · 시나리오명 · 설명(사용자 관점 흐름) · 연관 TC 수 · 근거(출처)</sub> |
| <sub>테스트케이스</sub> | <sub>19컬럼 = 설계 12(TC ID ~ 출처) + 실행 기록 7(실행결과 ~ 비고) · TC ID `TC-<대분류약어>-<3자리>`(입력 문서에 화면 ID 체계가 있으면 그 코드 기준)</sub> |

- 테스트케이스 19컬럼: `TC ID` · `대분류` · `중분류` · `소분류` · `시나리오 ID` · `우선순위` · `적용 기법` · `사전조건` · `테스트 절차` · `입력 데이터` · `기대결과` · `출처` · `실행결과` · `실제 결과` · `재현 절차` · `발견 환경` · `상태` · `결함 ID` · `비고`
- 출처: 입력 문서 위치(문서명 · 시트/페이지/섹션) 또는 `AI보완(기법명)`(예 `AI보완(경계값분석)`) · 빈 출처 = 오류
- 시나리오 = 사용자 여정 단위(예 「비회원이 주문 후 회원 전환」) · 케이스 = 그 안의 검증 단위
- 스타일: 헤더 진회색(#4A4A4A) · 흰 굵은 글씨 · 전체 테두리 · 머리행 고정 · 자동 필터 · 우선순위 상 = 연한 빨강 배경(#FCE4E4)

테스트 기간 내내 쓰는 문서 — 실행 기록 컬럼

| <div align="center"><sub>컬럼</sub></div> | <sub>쓰는 법</sub> |
|:---|:---:|
| <sub>실행결과</sub> | <sub>드롭다운 `Pass` · `Fail` · `Block` · `미실행`(셀 클릭 시 선택 목록) · Block = 실패가 아니라 선행 조건 문제로 시도 자체가 막힌 경우</sub> |
| <sub>실제 결과</sub> | <sub>Fail일 때 실제 동작 · 상세 오류 내용</sub> |
| <sub>재현 절차</sub> | <sub>테스트 절차와 다른 조작으로 발견했을 때만 기록</sub> |
| <sub>발견 환경</sub> | <sub>브라우저 · 기기 · 계정 등</sub> |
| <sub>상태</sub> | <sub>드롭다운 `신규` · `수정중` · `수정완료` · `재확인완료`(결함 처리 진행)</sub> |
| <sub>결함 ID</sub> | <sub>결함 관리 툴(지라 등)을 쓰는 프로젝트만 연결</sub> |

- 생성 시 실행결과만 `미실행` · 나머지 실행 기록 칸은 빈칸 → 실제 테스트 결과를 채우면 그대로 진척 보고의 원본

## 설치 · 단독 사용

```bash
cp -r skills/qa-master ~/.claude/skills/qa-master
```

- 리포 루트 기준 명령 · 스킬 일괄 설치는 원본 리포 `bash install-global.sh` · 공유 리포 `share/update.sh`
- 의존성: 모드 1 엑셀 생성 = Python 3 + `openpyxl`(`pip install openpyxl`) · Python이 없는 PC는 모드 1 실행 불가(Python 설치 또는 다른 PC에서 만든 엑셀 사용)
- 화면설계서 PDF를 읽기 도구로 렌더할 수 없는 환경 = PyMuPDF 추가 필요(페이지 → PNG 변환)
- 스크립트 위치: 플러그인 설치 시 `${CLAUDE_PLUGIN_ROOT}/scripts/make_tc_excel.py` · 로컬 실행 시 SKILL.md 폴더 기준 · `sys.path`에 scripts 폴더를 더해 `build_workbook()` 호출(스타일 · 드롭다운 코드 신규 작성 금지)
- 하네스 안에서: [`agent/test-runner`](../../agent/test-runner/README.md)
  - 이 스킬의 TC 엑셀을 정본 양식 그대로 실행(시트 3개 · 19컬럼 · 드롭다운 값 변경 금지 · 제출용 변형도 로드 가능)
  - TC 엑셀 없이 기획서만 있으면 test-runner의 tc-loader가 이 스킬 모드 1 호출 → 사용자 확인 → `input/{slug}/` 배치 후 실행
  - 사전 준비: 리포 루트에서 `./sync-skills.ps1`(또는 `bash ./sync-skills.sh`) 1회 → `agent/test-runner/.claude/skills/`로 복사
- 앞 단계 산출물 활용: [`requirements-generator`](../requirements-generator/README.md)의 요구사항 정의서 · [`ia-builder`](../ia-builder/README.md)의 IA 엑셀도 입력 문서로 사용 가능
